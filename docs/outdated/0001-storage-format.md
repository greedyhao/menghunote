## 项目背景

- **menghunote**：基于 GPUI（Zed 的 GPU 加速 Rust UI 框架，crates.io `gpui` 0.2.x）的笔记软件，桌面端优先，Windows 首要平台，语言 Rust。
- 单人开发起步，用 AI agent 团队协作编码（DeepSeek 执行、GPT 决策）。
- 笔记含富文本（标题 / 列表 / 代码块 / 引用）。

## 要决断的问题

**本地存储格式 + 数据流架构**：如何在 local-first（离线优先、本地为准）前提下，同时满足下面两条硬需求，并给出可执行落地步骤。

**需求 A — AI 对接**
- 笔记内容需切 chunk、算 embedding、做向量检索；
- 同时需要关键词/全文检索，支持按笔记、标签、时间过滤（即 hybrid search）；
- LLM 需能稳定拿到"检索 → 上下文拼装"的结果；
- AI 索引必须在笔记编辑后**增量更新**，不能每次全量重建。

**需求 B — 远端同步 + 可自建中心服务器**
- 多设备同步，用户可自行部署中心服务器（self-host）；
- 必须能处理冲突（同一笔记多端并发编辑）；
- 服务器角色可由轻到重，但架构不能堵死后续多人协作。

**需求 C — Typora 式所见即所得（新增，影响本决策）**
- 编辑体验对标 Typora：**Markdown 源码即真源**，渲染视图就是编辑界面；
- 语法标记（`#`、`**`、`-`、`>` 等）在非编辑状态下**不绘制**，光标进入该构造时显现；
- 这意味着：`**` 这类字符**真实存在于存储的文本中**，只是未被渲染。

> ⚠️ **这一条推翻了本简报初稿的前提**：不能把正文存成 CRDT 富文本（Loro Rich Text）。
> 富文本模式下 `**` 根本不存在于数据里，就无从"隐藏"。
> **正确形态是：Markdown 纯文本为唯一真源 + 渲染层派生样式**。
> 因此 CRDT 应使用**文本 CRDT**（`LoroText`，字符级），而非富文本 CRDT。
> 附带好处：纯文本对 AI 切块/embedding 天然友好，对导出/迁移也最安全。
> 编辑器侧的具体设计见 [`docs/briefs/0002-editor-core.md`](../briefs/0002-editor-core.md)。

## 候选方案

- **A. 纯 Markdown + frontmatter**，旁挂 SQLite 索引（Obsidian 类）
  纯文本透明、易导出、AI 友好；但**文件级冲突**、无事务、富文本靠约定、索引一致性弱。
- **B. SQLite 单文件为唯一真源**：FTS5 + 向量表，同步靠 CDC/oplog 或 cr-sqlite 多主合并
  事务与查询强；但 cr-sqlite 成熟度存疑，富文本 CRDT 语义要自己扛。
- **C. CRDT 文档为唯一真源**（Loro），磁盘存 `.loro` snapshot + 增量 update，服务器只做 relay + 持久化；AI 索引旁挂 SQLite 但为**派生、可重建**。
- **D. 混合**：正文用 CRDT（Loro），元数据 + 检索索引进 SQLite，索引全派生可重建。

7. **第一阶段最小实现**：5-8 个可执行步骤，明确每步产出。

## 附录：Lead 初步倾向（**非结论**，供 GPT 反驳）

以下只是提供对立面，降低 GPT 从零起跑的成本，**不作数**：

- 倾向 **D（修正版）**：**Markdown 纯文本是唯一真源**，CRDT 用**文本 CRDT**（`LoroText` 字符级，不用 Loro Rich Text），SQLite 只承担"可丢弃的派生索引"（FTS5 + 向量 + 元数据）。
  理由：两条硬需求性质不同——同步需要**操作语义**（合并、因果、离线改写），检索需要**关系查询**。
  用 SQLite 当唯一真源会逼着在 SQL 之上重造 CRDT 语义；用 CRDT 当检索引擎则会和 FTS5 打架。
- 因此主张：**AI 索引一定是派生的、可重建的**，删掉索引不丢用户数据。
- 存疑点，请重点裁断：
  1. **磁盘上到底放什么**：一个 `.loro` 容器（内含 Markdown 文本），还是**每篇笔记一个 `.md` 文件** + 旁挂 CRDT 状态？后者用户可读、可 git、可被任何编辑器打开，但文件级并发与索引一致性更难。这是本决策的核心分歧点。
  2. `sqlite-vec` 仍是 alpha，第一版是否干脆**不做向量检索**，先只做 FTS5 + 结构化过滤？（即"阶段化"）
  3. 中心服务器第一版是否**只做 relay + 加密 blob 存储**，不解析明文？这直接影响服务器信任模型。
  4. 既然真源是 Markdown 文本，**是否还需要 CRDT 才能同步**？还是可以做"文本 + 行级三方合并"的轻量方案（成本低但有信息丢失风险）？请明确二者边界。
