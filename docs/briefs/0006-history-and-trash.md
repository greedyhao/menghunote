# 0006 历史记录与回收站（后续开发备忘）

> 状态：**未开发，仅记录范围与待决问题**。等同步 v1 收口后再排期。
> 关联：ADR 0001（SQLite 真源）、ADR 0002 §8（undo/redo）、ADR 0006（同步/轮换）、`crates/storage/src/projector.rs`。

## 1. 现状

- 正文是 Loro CRDT；每篇笔记的完整 op log 在本地 `loro_updates`，snapshot 只加速；当前**没有本地历史裁剪**。
- 多设备合并保留所有 peer op；新设备 bootstrap 拿 `full_history` snapshot，所以历史会随同步过去。
- `notes` 行永不物理删除，`deleted=1` 墓碑；`projector::trashed_notes` 已有内部投影，但**没有回收站 UI**。
- 只有会话内 undo/redo（单 peer、750ms 合并、100 组、不跨重启）；没有"查看/恢复历史版本"。
- relay 侧 log 是事件流，7 天 GC 后旧密文被 checkpoint 取代；**历史仍在 full-history snapshot**，但 relay 日志不再是完整历史来源。

## 2. 目标能力（分阶段）

### H1 历史查看与恢复（只读优先）
- 按笔记查看时间线：时间、设备/操作者、变更摘要（可选 diff）。
- 支持"恢复到新分支/新文档"：不改写 CRDT 历史；是否允许"覆盖当前"需要单独确认。
- 数据来源：本地 `loro_updates` + snapshot；跨设备事件优先本地 op log，不依赖 relay 旧日志。
- 性能：大文档/长历史的分页与懒加载；不阻塞编辑。

### H2 回收站
- 列表、恢复、彻底删除；恢复要同步成反向 tombstone（多设备一致）。
- 彻底删除必须显式二次确认，并明确"其他设备/历史 snapshot 中是否仍存在"。
- 与同步/轮换的交互：删除与历史清理不能破坏 pin/基线覆盖证明。

### H3 保留策略与裁剪（需用户显式确认）
- 可选"保留最近 N 天/N 个 checkpoint"；裁剪会永久丢历史，默认关闭。
- 裁剪与同步：本地裁剪不回写历史；远端 full-history snapshot 仍可能保留旧内容 → 必须说明边界。
- 体积/性能预算：op log 增长对启动、搜索、checkpoint 的影响。

### H4 跨设备归属与审计（可选）
- 时间线显示来源设备；设备吊销后其历史是否仍展示（内容仍有效，身份状态另标）。
- 与轮换：历史内容跨 epoch 保留；旧 epoch 密文 7 天 GC 只影响 relay 副本，不影响本地明文历史。

## 3. 待决问题（开发前需 GPT/用户拍板）

1. **恢复语义**：恢复为新文档/新分支（推荐，append-only）还是覆盖当前（需要新的"反向 op + 冲突处理"）？
2. **历史粒度**：按 op、按编辑会话、还是按 checkpoint/天？UI 复杂度与存储成本不同。
3. **保留期限**：默认永久保留，还是默认 90 天/N 个 checkpoint？裁剪是否必须用户显式开启？
4. **删除语义**：彻底删除是否要跨设备"不可恢复"？历史 snapshot 中仍含内容时如何告知用户？
5. **隐私边界**：历史是本地明文；是否需要对历史做本地加密/单独密钥？（当前 ADR 0001 决策是本地明文。）
6. **relay 角色**：是否需要"历史专用 checkpoint"或"按文档 checkpoint"，还是只靠本地 op log + 现有 full snapshot？
7. **性能门禁**：长历史（例如 10 万 op）下的时间线加载、diff、恢复耗时上限。

## 4. 非目标（v1 不做）

- 管理员式"改写/删除过去 op"（CRDT append-only 不支持，也不应做）。
- 跨用户共享历史/审计日志（单用户多设备）。
- 在 relay 上做明文历史查询/搜索。

## 5. 验收草案

- H1：任意笔记可打开时间线；恢复到新文档后内容正确、旧历史不变；大文档加载 < 200ms（首屏）。
- H2：删除→回收站→恢复，多设备一致；彻底删除有二次确认与明确提示。
- H3：裁剪策略需显式开启、可预览影响、裁剪后同步/搜索/轮换不回归。
- 全程有真实 SQLite + Loro 测试；UI 需 Windows 真机验收。
